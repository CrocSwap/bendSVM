# Bounded SHA-256 first slice

This first slice supplies a generic C runtime adapter, a Node `crypto` SDK
reference, and an isolated native/SBF test harness. It does **not** add a
callable Bend intrinsic. The syscall adapter is ready for a later compiler
integration that can preserve the source proof boundary described below.

## Runtime contract

`runtime/bend_sha256.h` exposes `bend_sha256_hashv(parts, count, output)`. It
hashes the concatenation of the parts in order, without adding length framing.
The initial bound is 16 slices and 1,024 total bytes. Empty slices count toward
the slice limit; zero slices hash the empty message. The digest is the raw 32
bytes in SHA-256 output order.

The syscall declaration matches the pinned local Solana 2.3 ABI:

```c
u64 sol_sha256(const u8 *vals, u64 val_len, u8 *hash_result);
```

`vals` points to consecutive 16-byte descriptors with a 64-bit address followed
by a 64-bit length. `val_len` is the descriptor count, not a byte count. The
header asserts the descriptor layout and 64-bit pointer size. This matches
`solana-define-syscall 2.3.0`, `solana-sha256-hasher 2.3.0`, and the Agave
2.3.13 BPF loader used by the pinned LiteSVM 0.7.1 dependency graph. Its hash
handler maps each descriptor and feeds its bytes to the hasher in order.

The wrapper checks count, total length, null nonempty slices, pointer-range
arithmetic, and output overlap before calling the syscall. It calls into a
private 32-byte digest buffer and copies to `output` only after a zero syscall
status. Thus validation failures and an explicit nonzero syscall return leave
caller output unchanged. The pinned Agave runtime returns success or aborts the VM; its nonzero C-return
path is exercised only with the injected native mock. The result carries the wrapper status and, for a
syscall failure, the exact nonzero syscall status. Solana VM faults are surfaced
by LiteSVM as failed transactions rather than normal C returns.

The wrapper cannot establish that an arbitrary non-null pointer is mapped and
readable. Callers must provide a live, aligned descriptor array and readable
nonempty slices for the duration of the call, and must keep inputs unchanged.
The output must be writable and disjoint from both descriptors and all input
byte ranges. Input slices may overlap one another. The wrapper never writes to
an input range. These assumptions are part of the ABI contract, not checks the
header can prove.

The offchain [`sdk/sha256.ts`](../sdk/sha256.ts) API accepts readonly byte-view
arrays, rejects overlimits explicitly, leaves inputs unchanged, and returns raw
digest bytes. It uses `node:crypto` as the offchain reference. It rejects detached buffers, views made out of bounds by resizing, and shared
memory-backed views because another worker could mutate their bytes during a
synchronous hash operation.

## Source-facing proof boundary

The current backend rejects unsafe/foreign dependencies in
[`compiler/backend.ts`](../compiler/backend.ts) and only lowers known Base
primitives after checking Base provenance and their exact signatures. The build
also rejects undefined SBF imports outside its explicit allowlist in
[`scripts/build.ts`](../scripts/build.ts). Those gates must stay fail-closed.

A safe source entry needs a real checked SHA-256 meaning. A Bend function with a
placeholder body cannot justify replacing that body with a syscall: proof
checking would reason about different behavior. The smallest acceptable next
integration is a compiler-owned, uniquely identified binding with an exact
checked signature and provenance, backed by a safe SHA-256 reference definition
whose semantics the checker sees. Lowering may specialize only that exact
binding to `bend_sha256_hashv`; same-name user definitions, changed signatures,
foreign/unsafe definitions, and unproven shadow bindings must still reject.
The checker’s model of the reference definition, the specialization rule, and
the runtime/syscall equivalence remain explicit trust assumptions. A law may
state the 32-byte SHA-256 result for a concrete preimage, but it must not claim
collision freedom. Callers that hash structured values need domain separation
and unambiguous length framing.

The source API candidate is:

```text
ByteView                         // opaque, immutable, borrowed for this call
HashParts<16>                    // at most 16 views and at most 1,024 bytes total
Digest256                        // exactly 32 output bytes, in SHA-256 byte order
Crypto.sha256_bounded(parts) -> Hashed{digest} | TooLong{}
```

`ByteView` must not be constructible from arbitrary integers, serializable,
stored, or allowed to escape its checked call scope. The checked reference body
must implement the same FIPS SHA-256 semantics and limits; `TooLong` must reject
the whole input instead of returning a prefix hash. The binding should be
introduced through a pinned compiler-owned/Base definition so its identity is
not inferred from a spelling in application source.

That source binding and its backend specialization are outside this slice’s
owned files, so this report does not claim Bend source code can call the
intrinsic. Required host-owned integration changes are:

- Add the exact compiler-owned binding/provenance and checked reference body;
  add narrowly scoped backend specialization with exact signature checks.
- Include the runtime header in generated integration and permit exactly the
  `sol_sha256` import in the SBF build allowlist.
- Register the foundation test separately from future source-binding acceptance.
  Source-binding acceptance must include negative proof-gate cases for foreign,
  shadowed, and signature-mutated bindings.

## Executable evidence

`tests/sha256.ts` exercises the SDK and static vectors, builds a C ABI mock under
AddressSanitizer and UndefinedBehaviorSanitizer, compiles a generic SBF test
entrypoint with Anza platform-tools v1.53, verifies the exact undefined-import
set (`sol_sha256`, `sol_set_return_data`, and the existing runtime
`sol_memset_`) and compiler stack report, then runs the ELF in LiteSVM 0.7.1 using a
private Cargo manifest/lockfile and `target/sha256`.

Vectors cover empty input, empty slices, `abc`, padding boundaries 55/56,
63/64/65 and 127/128/129 bytes, 16 slices, and 1,024-byte single/multipart
inputs. Tests compare multipart and concatenated hashing, enforce 16-slice and
1,024-byte boundaries, check input immutability, preserve output on explicit
mock-syscall failures, and compare the actual SBF syscall result byte-for-byte
with the frozen vectors. LiteSVM records consumed compute units per vector; the
Clang `.su` output records native SBF frame size. Both are included in each
successful run report.

From the repository root, run:

```sh
./node_modules/.bin/bun tests/sha256.ts
```

Select `SBF_TOOLS` if the pinned compiler is not at
`~/.cache/solana/v1.53/platform-tools/llvm/bin`. The runner requires Rust/Cargo
1.92.0. It creates a unique directory under ignored `build/sha256/`; it writes a
`report.json` only after every stage passes and never replaces prior reports.
Inputs and tool identities are hashed before work and checked again before
publication; Cargo JSON identifies the one test binary actually executed.
The report contains hashes of source inputs, each vector preimage and encoded
instruction, the native/SBF/Cargo test artifacts, compiler outputs, and tool
binaries, along with measured CU and frame evidence. A failed or incomplete run
does not produce a success report.

These tests establish this wrapper’s bounded behavior on the recorded inputs
and toolchain. They do not prove collision resistance, arbitrary pointer
validity, the correctness of a future Bend binding, end-to-end compiler
correctness, or production readiness.


`npm run test:sha256-receipt` runs private full-driver failure probes after a
successful foundation run. Nonzero compiler exit, source drift and ELF drift
must refuse publication and preserve prior evidence. Recorded shims reuse the
accepted Rust test binary; these probes validate receipt behavior. Compiler
binaries and Cargo's source-to-executable association remain trusted components,
with their identities recorded for inspection.
