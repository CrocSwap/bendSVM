# Developer workflow milestone

Status: accepted. See [the acceptance review](developer-workflow-acceptance.md).

Objective: a developer can create, build, verify, and exercise a Bend account-backed
program without writing C, manually encoding instructions, or learning compiler internals.

## Deliverables and acceptance

1. One documented command surface for creating a project, checking compatibility,
   building SBF and its client, checking declared source laws, and exercising it offline.
2. A fresh project template with an authorized account-backed collection program,
   declared laws/proofs, storage configuration, readable tests and a getting-started guide.
   Creation refuses to overwrite existing work. Paths with spaces must work.
3. Generated TypeScript instruction methods and value types from checked schema and
   storage interface. Account names/order/flags and canonical bytes come from the ABI;
   callers do not supply tags, padding or account offsets. Include state/window decoding.
   Support existing single-account, multi-account and collection ABIs, with explicit
   diagnostics for unsupported or malformed descriptors. Dynamic CPI/token remaining
   accounts remain explicit because the ABI alone does not express application policy.
4. A reusable LiteSVM runner behind the test command. Fresh generated-project tests
   submit signed transactions, create actual state/collection accounts, decode results,
   and assert persistence, authorization failures and unchanged accounts on rejection.
   Developers write high-level test calls, not Rust or C adapters.
5. Meaningful tests: generated bytes match existing independent fixtures; generated
   clients execute actual SBF; client misuse fails clearly; changes to a template's
   behavior and laws produce test/proof failures. Test a fresh project end to end and
   another independent existing program through the same workflow.
6. Documentation distinguishes source law checking, optional application-specific SMT
   proofs, execution testing and live deployment. No claim that arbitrary new programs
   acquire full formal verification automatically. Network access is not required for
   the local workflow once existing toolchain dependencies are installed.

The final acceptance review must map each item to current command results and
artifacts. The preceding collection milestone remains separate historical evidence.

## Incremental evidence

`sdk/program-client.ts` provides named instruction calls, account order/permissions,
canonical encoding, state/collection decoding and allocation sizes across ABIs 1–3.
SDK keys accept base58 addresses and SDK U64 values accept bigint. Remaining effect
accounts are explicit. `compiler/client.ts` emits TypeScript types and named methods
using this runtime; it does not duplicate the canonical codec.

`node_modules/.bin/bun tests/program-client.ts` passes existing ABI 1/2/3 descriptor
checks, independent collection/queue instruction-byte expectations, initialization
account flags, generated-module invocation, collection decoding and malformed-call
rejections. The separate end-to-end gate now executes generated clients against SBF.

Public builds now emit a portable JavaScript client and typed TypeScript client
with a local bundled runtime. Client files are included in manifests, along with
their SDK dependencies. The final fresh collection/queue builds reproduce the
client files; existing vault/vesting/exchange public builds also remain byte-identical.

`tests/client-packaging.ts` copies the client to a temporary directory outside the
repository, executes it, and uses the pinned `node_modules/typescript@5.2.2` in
strict mode to check valid calls and expected failures for wrong amounts, missing
accounts, extra arguments and unknown instructions. `TSC_JS` is an optional
override only when it reports the same pinned version; a host TypeScript cache is
not an acceptance dependency.

`npm run bend -- <new|check|verify|build|test> <directory>` now wraps a signed-owner
collection template with three declared laws. `tests/project-commands.ts` passes
fresh creation, target checking, source-law checking and SBF/client build in paths
containing spaces. Existing paths are preserved; source mutations contradicting
the declared laws and proof holes fail verification/build.

The generic offline runner executes signed system/program transactions and reads
accounts through the TypeScript test context. End-to-end tests pass for a fresh
collection and existing single/multi-account programs: 14 transactions, including
five expected rejections, and 31 assertions. A payload mutation passes the unrelated
source laws but fails the execution test. Empty tests cannot produce acceptance.

All 78 existing SBF regression tests pass (zero failures, three benchmark-only tests
ignored by that runner). Portable-client execution, strict client type checks,
reproducible artifacts and current report hashes passed the final audit recorded
in `build/developer-workflow-acceptance.json`. No work remains in this milestone's
six requirements; live deployment remains a separate task.
